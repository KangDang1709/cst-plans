2. Lambda Functions & Firebase Integration

POST /create-exam-room

Request Body (from US-2 Modal)

{
  "roomName": "Kiểm tra Toán Chương 3",
  "subject": "Toán",
  "grade": "Lớp 6",
  "durationMinutes": 60,
  "mode": "auto_advance",
  "assignmentId": "assign123",
  "publishNow": true,
  "scheduledStartAt": null
}

Handler Flow

  1. Validation
    • JWT → extract teacherId
    • Fields: roomName, subject, grade, durationMinutes (15-180), mode, assignmentId
    • If publishNow=false: verify scheduledStartAt is future timestamp
  2. External Validation
    • Assignment Service: GET /assignments/{assignmentId} → validate + question count
    • Verify subject + grade are valid
  3. Generate IDs
    • examRoomId = UUID
    • joinCode = 6-char alphanumeric (A-Z, 0-9), verify unique
  4. Create DynamoDB
    • state = "WAITING" (both flows)
    • If publishNow=true: startedAt=now() (teacher enters waiting room 10 min early)
    • If publishNow=false: scheduledStartAt=provided, startedAt=null (await scheduler)
  5. Firebase Conditional
    • Flow 1 (publishNow=true): Write to state node with startedAt + durationMinutes
    • Flow 2 (publishNow=false): NO WRITE (wait for scheduled time)
  6. Response
    • Return 201: examRoomId, joinCode, state, scheduledStartAt
    • FE Flow 1: Redirect to Waiting Room
    • FE Flow 2: Show success popup with room code + copy button
✓ Flow 1: publishNow=true → Firebase write now → students can join
✓ Flow 2: publishNow=false → Lambda scheduler monitors scheduledStartAt → Firebase write at time

POST /start-exam (Teacher) — Flow 1 Only

Note: Only if room created with publishNow=true. If publishNow=false (scheduled), DO NOT show this button — scheduler handles state transition.

Handler Flow

  1. Validate JWT + examRoomId ownership
  2. Verify room state = "WAITING" AND publishNow=true
  3. Calculate durationMs = durationMinutes * 60_000
  4. Update DynamoDB: Set state→"IN_PROGRESS", startedAt→now()
  5. Firebase WRITE: Update exam-rooms/{examRoomId}/state with:
    {
  "state": "IN_PROGRESS",
  "startedAt": 1705315200000,
  "durationMinutes": 90,
  "eventCount": 0,
  "timestamp": 1705315200000
}
  6. Both FE + Unity receive notification via Firebase listener
  7. Return 200 OK
⚠️ Firebase write targets same node regardless of action. Concurrent /start requests will overwrite each other (OK — idempotent state update).

POST /join-exam (Student)

Handler Flow

  1. Validate JWT (student token) → extract studentId
  2. Query by joinCode (GSI) → get examRoomId + room details
  3. Verify room state ∈ ["WAITING", "IN_PROGRESS"] (can't join after ENDED)
  4. Write DynamoDB ExamParticipants: Create entry with joinedAt=now(), hasSubmitted=false
  5. Firebase WRITE: Update exam-rooms/{examRoomId}/state (increment eventCount or update timestamp)
    {
  "state": "...",
  "eventCount": 5,
  "timestamp": 1705315300000
}
  6. Teacher receives Firebase notification → calls GET /participants → sees new student
  7. Return examRoomId + room metadata (durationMinutes, startedAt if IN_PROGRESS)

POST /submit-answers (Student)

Handler Flow

  1. Validate JWT (student token)
  2. Verify room state = "IN_PROGRESS" (can submit during exam only)
  3. Validate answers against Assignment Service: GET /assignments/{assignmentId}/questions
  4. Write DynamoDB ExamSubmissions: Create submission record with timestamp
  5. Update DynamoDB ExamParticipants: Set hasSubmitted=true, submittedAt=now()
  6. Firebase WRITE: Update exam-rooms/{examRoomId}/state (increment eventCount)
    {
  "state": "IN_PROGRESS",
  "startedAt": 1705315200000,
  "durationMinutes": 90,
  "eventCount": 2,
  "timestamp": 1705315350000
}
  7. Teacher receives Firebase notification → calls GET /participants → sees submission count increased
  8. Return 201 Created + submissionId
⚠️ Concurrent submissions (CR7 + Messi at same time) both target same Firebase node. Last write wins — but eventCount may not increment properly. Consider: atomically increment eventCount in Lambda BEFORE writing to Firebase.

POST /end-exam (Teacher)

Handler Flow

  1. Validate JWT + examRoomId ownership
  2. Verify room state = "IN_PROGRESS" (can't end if not started)
  3. Update DynamoDB ExamRooms: Set state→"ENDED", endedAt→now()
  4. Query ExamSubmissions + ExamParticipants for results
  5. Firebase WRITE: Update exam-rooms/{examRoomId}/state with:
    {
  "state": "ENDED",
  "endedAt": 1705332000000,
  "timestamp": 1705332000000
}
  6. Both FE + Unity receive notification
  7. Teacher calls GET /results; students see end screen
  8. Return 200 OK

GET /participants (Teacher)

Handler Flow

  1. Validate JWT + examRoomId ownership
  2. Query DynamoDB ExamParticipants where examRoomId = X
  3. Return array with all students: name, joinedAt, hasSubmitted, submittedAt
  4. No Firebase read (REST is source of truth for data)
✓ Called by FE after Firebase notification of /join or /submit

GET /results (Teacher)

Handler Flow

  1. Validate JWT + examRoomId ownership
  2. Verify room state = "ENDED" (can't get results before end)
  3. Query DynamoDB ExamSubmissions + ExamParticipants
  4. Join with Question answers (from Assignment Service)
  5. Calculate scores, sort by submission time
  6. Return leaderboard array

Scheduled Exam Processor (Flow 2 — publishNow=false)

Purpose

Periodically checks for exams with scheduledStartAt in the past + state=WAITING. When scheduled time arrives, automatically transitions state → IN_PROGRESS and writes to Firebase.

Implementation Options

  • Option 1: CloudWatch Event + Lambda (AWS Native)
    • CloudWatch rule: Trigger every 1 minute
    • Lambda: Query ExamRooms where scheduledStartAt ≤ now() AND state=WAITING
    • For each: Update state→IN_PROGRESS, write to Firebase
    • Cost: ~43K invocations/month = ~$1 (minimal)
  • Option 2: DynamoDB Streams (Event-Driven)
    • Monitor room creation events
    • Lambda: Register scheduledStartAt in SQS/SNS delayed queue
    • Trigger handler at scheduled time
    • More complex setup, better for high throughput

Processor Handler Flow

  1. Query DynamoDB: SELECT * FROM ExamRooms WHERE scheduledStartAt ≤ now() AND state='WAITING'
  2. For each room:
    • Update: state→"IN_PROGRESS", startedAt→now()
    • Firebase WRITE: Update state node with startedAt + durationMinutes
    • Both FE + Unity get notifications instantly
  3. Log processed rooms for monitoring
✓ Automatic state transition at scheduled time
✓ Students see Firebase notification and can start exam
✓ Teacher can also manually call POST /start-exam if needed

3. Firebase Realtime Database Setup

Database Structure

exam-rooms/
  ├── {examRoomId}/
      └── state: { state, startedAt?, durationMinutes?, endedAt?, eventCount, timestamp }
      └── (no persistent event history — ephemeral only)

Firebase Initialization in Lambda

Node.js / TypeScript
import * as admin from 'firebase-admin';

// Initialize once at module level
const serviceAccount = JSON.parse(process.env.FIREBASE_CREDENTIALS);
admin.initializeApp({
  credential: admin.credential.cert(serviceAccount),
  databaseURL: process.env.FIREBASE_DB_URL
});

const db = admin.database();

// On state change, write to Firebase
async function updateExamState(examRoomId: string, state: any) {
  await db.ref(`exam-rooms/${examRoomId}/state`).set({
    ...state,
    timestamp: Date.now()
  });
}

Firebase Rules (Security)

{
  "rules": {
    "exam-rooms": {
      "$examRoomId": {
        "state": {
          // Only Lambda writes (via service account)
          ".write": "auth.uid === 'lambda-service-account-uid'",
          // FE + Unity can read
          ".read": "auth != null"
        }
      }
    }
  }
}

4. Infrastructure & Deployment

AWS Lambda Configuration

Environment Variables

  • DYNAMODB_EXAM_ROOMS_TABLE = "ExamRooms"
  • DYNAMODB_EXAM_SUBMISSIONS_TABLE = "ExamSubmissions"
  • DYNAMODB_EXAM_PARTICIPANTS_TABLE = "ExamParticipants"
  • FIREBASE_DB_URL = "https://your-project.firebaseio.com"
  • FIREBASE_CREDENTIALS = JSON service account key
  • IDENTITY_SERVICE_URL = "https://identity-service.internal"
  • ASSIGNMENT_SERVICE_URL = "https://assignment-service.internal"

Runtime & Dependencies

  • Node.js 20.x (or C# 8.0 if using .NET Lambda)
  • firebase-admin@latest
  • aws-sdk v3 (DynamoDB client)
  • Timeout: 30s (sufficient for serial DynamoDB + Firebase writes)
  • Memory: 512MB (default)

IAM Permissions (Lambda Execution Role)

  • dynamodb:PutItem, dynamodb:UpdateItem, dynamodb:GetItem, dynamodb:Query on ExamRooms, ExamSubmissions, ExamParticipants
  • dynamodb:GetItem with GSI on joinCode
  • No S3 needed (questions fetched from Assignment Service)

DynamoDB Indexing

ExamRooms Table

  • Primary Key: examRoomId (HASH)
  • GSI: joinCode → allows rapid lookup by student code
  • TTL: Optional — set on endedAt to auto-delete old exams (e.g., 90 days)

ExamSubmissions Table

  • Primary Key: submissionId (HASH) + examRoomId (RANGE)
  • GSI: examRoomId + submittedAt → query results by room

ExamParticipants Table

  • Primary Key: participantId (HASH, format: examRoomId#studentId)
  • GSI: examRoomId + joinedAt → list all students in room

Error Handling & Logging

Errors from Each Endpoint

  • 400 Bad Request — Invalid JWT, missing fields, invalid assignmentId
  • 401 Unauthorized — Invalid/expired JWT, mismatched teacherId
  • 403 Forbidden — Teacher trying to access student data, vice versa
  • 404 Not Found — examRoomId not found, joinCode not found
  • 409 Conflict — State transition invalid (e.g., /start on room already IN_PROGRESS)
  • 500 Internal Server Error — DynamoDB/Firebase failure

Logging Strategy

console.log(JSON.stringify({
  timestamp: new Date().toISOString(),
  level: 'INFO',
  action: 'start-exam',
  examRoomId: 'xyz',
  teacherId: 'abc',
  durationMinutes: 90,
  dynamoSuccess: true,
  firebaseSuccess: true,
  duration_ms: 245
}));
  • Log all DynamoDB writes with success/failure + latency
  • Log all Firebase writes + eventCount (for concurrency tracking)
  • Log any failed calls to external services (Identity, Assignment)
  • Use CloudWatch Insights to query by examRoomId or error rate

  • ✓ Identity Service integration tested

Testing
  • ✓ Unit test: DynamoDB writes succeed
  • ✓ Unit test: Firebase writes succeed
  • ✓ Integration test: Create room → Join → Start → Submit → End (full flow)
  • ✓ Concurrency test: 10 students submit simultaneously (eventCount increments properly)
  • ✓ Edge case: Student joins after exam ended (should fail with 409)
  • ✓ Edge case: Teacher starts exam twice (should succeed idempotently or fail with 409)
  • ✓ Error handling: Simulate DynamoDB timeout → Lambda should retry + return 500
  • ✓ Firebase listener: Verify FE + Unity receive notifications within 1s
Post-Deployment Monitoring
  • Monitor DynamoDB latency (should be <100ms)
  • Monitor Firebase write latency (should be <500ms)
  • Alert on Lambda failures (error rate > 1%)
  • Alert on concurrent write conflicts (check eventCount increments)
  • Log exam duration + submission count for capacity planning
